Décisions d'ancrage (prises ici — ne pas rouvrir)

  1. baseCommand: [python, -m, tiny_wae, <cmd>] comme le veut le chapeau. ⚠ Ce python en dur n'enfreint PAS la règle façade : un .cwl est destiné à un exécuteur externe (worker PID-FLOW), il ne peut pas connaître just. La règle façade s'applique aux recettes, à la doc et aux prompts — écris cette justification dans cwl/README.md, pour que personne ne « corrige » ces fichiers plus tard.
  2. La recette just cwl ne fait QUE de la validation statique : cwltool --validate sur les 3 fichiers, et rien d'autre. ⛔ Aucune exécution réelle dans le gate (l'oracle O2 est explicitement « local, hors gate » : il fait du réseau).
  3. ⭐ L'oracle O3 mérite mieux qu'une redite. L'invariant « STDOUT du step search = JSON parsable seul » est déjà couvert par les tests de l0-02.2. Ce qu'il faut tester ICI, et qui n'existe nulle part ailleurs, c'est la cohérence entre les .cwl et les CLI réels : un test pytest qui charge les 3 fichiers CWL (ce sont des YAML — yaml.safe_load) et vérifie que chaque inputBinding.prefix déclaré correspond à une option réellement exposée par le CLI correspondant. Motif : le jour où une option du CLI est renommée, la validation cwltool --validate restera verte (elle ne connaît pas nos CLI) et le workflow cassera silencieusement en production. C'est le seul test de cette fiche qui échouerait sur du code faux.
  4. Chaînage du workflow : search écrit son enveloppe via --json <fichier> (et NON par capture de STDOUT — c'est plus robuste en CWL et l'option existe pour ça), le step ingest la consomme par --acquisitions. Déclare l'enveloppe en outputBinding.glob.
  5. cwl/README.md : conventions, écart assumé vs cwl-assets (package installé, pas de scripts rsyncés), périmètre (⛔ PAS d'enregistrement server, PAS de pid:Milestone — retiré du périmètre en revue v2, c'est du scope creep), la justification du python en dur (décision n°1), le choix de successCodes (voir ci-dessus), et les commandes de validation et de run local.

Découvertes de terrain (l'exécution réelle a corrigé la conception)

  1. ingest.cwl ne capture AUCUNE sortie CWL (outputs: []). La première version tentait outputBinding.glob: $(inputs.data_root) en Directory : cassé à l'exécution — la spec CWL interdit un glob commençant par /, or data_root est justement pensé pour recevoir un chemin absolu externe au sandbox (c'est l'usage même de l'oracle O2). La sortie a été retirée plutôt que contournée ; le succès est signalé par le code de sortie.
  2. --sites-path / --settings-path doivent être passés explicitement à tout run CWL : le CLI défaut sur un chemin relatif au CWD, lequel est le répertoire de staging temporaire de cwltool, pas le dépôt. L'échec est trompeur (Settings.__init__() missing ... arguments, et non « fichier introuvable »).

⚠ Correction apportée à la revue : règle façade

Le README documentait le run local par un pixi run cwltool … en direct, avec une note l'assumant comme exception. Ce n'en est pas une : la règle du projet dit pixi ni dans la doc, ni dans les fiches, ni dans les prompts. Une recette just cwl-run <fichier> <args> a été ajoutée au justfile et le README l'utilise. Motif : le jour d'une bascule pixi↔uv, une occurrence dispersée dans un README est exactement ce qu'on ne retrouve pas.
