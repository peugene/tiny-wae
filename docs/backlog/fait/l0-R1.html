1. Arborescence : cwl/ devient assets/cwl/

assets/cwl/workflows/tiny-wae/1.0/workflow.cwl

Hiérarchie symétrique du cwl-store PID-FLOW (dépôt cwl-assets, ADR-0010 / EVO-42). L'identité d'un artefact est le nom de son RÉPERTOIRE — tous les fichiers s'appellent tool.cwl ou workflow.cwl, en version 1.0. Les 3 tools sont des tools partagés ; le workflow les référence en run: ../../../tools/<nom>/1.0/tool.cwl.

2. Trois contraintes PID-FLOW, découvertes en séquence

Chacune a le même profil, et c'est la leçon de fond de cette fiche : cwltool --validate reste vert alors que PID-FLOW refuserait l'artefact, ou pire, l'exécuterait en perdant silencieusement une sortie. L'exécuteur de développement est plus permissif que celui de production.

  • InlineJavascriptRequirement non supporté. L'exigence n'apportait rien : les tools n'utilisaient que des références de paramètre, sous-ensemble toujours disponible sans exigence déclarée.
  • EnvVarRequirement non supporté → l'input data_root disparaît avec lui (il n'aurait plus par quel moyen atteindre le process). TINY_WAE_DATA_ROOT est posée dans l'environnement du worker, hors CWL. Corollaire local mesuré : cwltool n'expose au job qu'un environnement minimal — une variable posée dans le shell appelant n'atteignait pas le job. D'où --preserve-environment TINY_WAE_DATA_ROOT dans just cwl-run, qui reproduit en local le comportement du worker.
  • ⛔ Plus aucune expression CWL, pas même une référence de paramètre. Le dépôt cwl-assets porte le constat (tool AppendToFile, TOOL-6) : un glob $(inputs.…) « ne matchait rien » côté PID-FLOW et la sortie était perdue SANS erreur. Le glob du tool search devient le littéral "acquisitions.json", tenu synchronisé avec le défaut de l'input json_out par un test dédié — le lien que l'expression portait gratuitement.

3. Conventions de contenu (cwl-assets)

  • label = nom de l'artefact (c'est lui qui identifie la brique côté IHM) ; la phrase descriptive passe en doc. label + doc sur chaque input, output et step.
  • hints: SoftwareRequirement / package: python sur chaque tool. Sans cette capability, le worker ne prend pas la tâche et elle reste en attente sans erreur — un échec muet de plus.

4. baseCommand : le point d'entrée console

[project.scripts] tiny-wae = "tiny_wae.__main__:app" génère un exécutable tiny-wae dans le bin/ de l'environnement d'installation ; les 3 tools l'appellent en baseCommand: [tiny-wae, <sous-commande>].

Pourquoi pas python -m tiny_wae : les deux formes échappent à la réécriture du worker (qui ne vise que les baseCommand pointant un .py relatif), donc l'exécutable est résolu sur le PATH du job dans les deux cas. Mais python est le nom le plus surchargé du système : résolu sur un autre interpréteur que celui du venv, il démarre puis échoue sur No module named tiny_wae — une erreur qui parle d'un module alors que le problème est un interpréteur. tiny-wae est unique au projet : absent du PATH, il échoue franchement.

Mesuré : cwltool transmet au job l'intégralité du PATH parent (seuls HOME, PWD et TMPDIR sont recréés), donc le bin/tiny-wae de l'env pixi est trouvé sans rien déclarer.

5. Le contrat de la wheel était faux

[project.dependencies] ne déclarait que typer/pyyaml/httpx/pystac-client. Les natifs (rasterio, pyproj, pillow) ne vivaient que dans [tool.pixi.dependencies], numpy nulle part (transitif de rasterio sous conda), et affine non plus alors qu'il est importé directement par core/geometry.py et adapters/chips.py.

Conséquence mesurée sur un venv nu : pip install réussit, puis tiny-wae version meurt sur ModuleNotFoundError: No module named 'numpy'. Le paquet s'installe et casse à l'import — c'est-à-dire chez le worker PID-FLOW, au premier run. Invisible en dev, puisque pixi installe aussi la liste conda.

Ajoutés au contrat : numpy>=2.0, rasterio>=1.4, affine>=2.4, pyproj>=3.6, pillow>=11.0. Les trois natifs restent aussi dans [tool.pixi.dependencies] : là c'est le choix de la source pour l'env de dev (builds conda-forge), ici c'est le contrat de livraison.
