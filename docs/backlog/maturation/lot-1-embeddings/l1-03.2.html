Révisée post-revue v1 (E-1, K-08/S-10, C-24) : dépendances réalignées sur le double (plus d'arête vers Clay — c'est ce qui rend le chapeau parallèle à l1-02) ; l'oracle d'échec ne touche PLUS aux manifestes du Lot 0. Révisée post-revue v3 (V-10, V-16, E-23, A-14) : dépend de l1-00, qui pré-pose les clés de settings.yaml (plus d'écriture concurrente) ; l'option --cloud-max n'était oraclée nulle part alors que deux fiches en dépendent ; la sémantique de reprise d'un .error.json n'était écrite nulle part.

Objectif

Parcourir les acquisitions d'un site sur une fenêtre, calculer les vecteurs manquants, les ranger, et ne rien recalculer au second passage.

Contexte et périmètre

src/tiny_wae/cli/embed.py.

⚠ Lire cli/ingest.py avant d'écrire. Ce CLI en est le frère : mêmes codes de sortie (ceux du chapeau l0-01 — renvoi, pas de recopie), logs sur STDERR, résumé de compteurs, aucune donnée mélangée aux logs.

Interface :

just run embed --site A01 --from 2024-01-01 --to 2024-12-31 --model clay-v1.5 [--force] [--cloud-max N]

Comportement :

  • parcourt <data_root>/<site>/*/manifest.json, retient les status == "ingested" dans la fenêtre ;
  • ⭐ écarte ceux dont cloud_pct > embed_cloud_pct_max (défaut 10) et les compte dans un compteur dédié skipped_cloud. ⭐ Précédence à trois niveaux, à respecter et à oracler (revue v3, V-16) : --cloud-max (option) > TINY_WAE_EMBED_CLOUD_PCT_MAX (env) > settings.yaml. C'est l'option que la checklist humaine de l1-05.3.H utilise, et elle n'était exercée par aucun oracle. ⚠ Deux points d'ancrage dans le code existant (revue v3, V-10/A-5) : la clé est pré-posée par l1-00 dans config/settings.yaml — cette fiche consomme, elle n'écrit pas dans ce fichier ; et embed_cloud_pct_max doit figurer dans adapters/config_io.py::_INT_FIELDS, sans quoi la surcharge par environnement rend une chaîne et le contrôle de bornes de core/settings.py::validate() lève un TypeError illisible au lieu d'une erreur de configuration ;
  • pour chacun : charge le tenseur (l1-01.2), embedde (l1-01.3 → adapter), écrit (l1-03.1) ;
  • ⭐ saute ceux dont la clé d'idempotence stockée égale la clé courante → skipped. --force recalcule quand même ;
  • compte et publie : found, skipped_cloud, embedded, skipped, failed, avec le dénominateur.

⭐ Invariant de conservation, sur le modèle du Lot 0 : found == skipped_cloud + embedded + skipped + failed. Il doit lever s'il ne boucle pas.

Le CLI accepte n'importe quel model_id du registre — y compris le double, ce qui permet de tout vérifier sans poids.

⭐ Sémantique de reprise d'un .error.json (revue v3, E-15 — n'était écrite nulle part) : un .error.json est une trace de diagnostic, jamais un marqueur de skip. Un run suivant rejoue l'item comme s'il n'y avait rien, et supprime le fichier d'erreur en cas de succès. La règle inverse — traiter l'erreur comme « déjà traité » — produirait un corpus incomplet silencieusement, avec des compteurs qui bouclent : exactement le type de défaut que l'invariant de conservation ne peut pas attraper.

⭐ Taxonomie des CLI : src/tiny_wae/__main__.py déclare en docstring une « taxonomie fermée du lot (9 sous-commandes) ». Le Lot 1 la porte à 15 : c'est cette fiche, premier CLI ajouté, qui met la docstring à jour — les suivantes n'y touchent plus. Aucun test ne l'asserte aujourd'hui ; ne pas en écrire un pour ça, c'est de la documentation.

Hors périmètre : le parcours multi-sites (l1-03.3) · toute mesure de temps (l1-04.1 instrumentera ce code de l'extérieur) · toute qualité.

Oracle / recette (figé AVANT implémentation)

# Critère mesuré Seuil de succès
O1 Run sur les 4 fixtures avec le double, seuil à 10 % compteurs exacts, gelés dans le test ; l'invariant de conservation boucle ; un vecteur + un compagnon par item embeddé
O2 ⭐ Run double — témoins positif ET négatif 1er run : embedded > 0, skipped == 0 · 2e run : embedded == 0, skipped == embedded du 1er. Sans le témoin positif, un CLI qui ne ferait rien passerait. ⚠ Ne pas asserter ici « vecteurs identiques au bit près » : après « 0 recalcul », c'est tautologique — les fichiers n'ont pas été touchés (revue v3, E-23). Le déterminisme réel se mesure en 3e passage avec --force (O3), seul cas où le vecteur est effectivement recalculé, ou par comparaison des mtime
O3 --force au 3e run recalcule tout : embedded retrouve sa valeur du 1er run, et les vecteurs recalculés sont identiques au bit près aux premiers (le double est déterministe) — c'est ici, et pas en O2, que l'identité se mesure
O4 ⭐ Filtre nuage, dans les deux sens la fixture à cloud_pct > 10 est en skipped_cloud et n'a pas de vecteur ; avec le seuil relevé à 100, elle est embeddée. Le seuil discrimine réellement
O4b ⭐ Précédence des trois niveaux settings.yaml à 10, env à 50, --cloud-max 90 : le run retient 90 ; sans l'option, 50 ; sans l'env, 10. Trois assertions — c'est le seul oracle qui exerce l'option dont l1-05.3.H dépend
O4c Surcharge par environnement, valeur non entière ("abc") erreur de configuration lisible, pas un TypeError de comparaison — c'est le témoin de l'ajout à _INT_FIELDS et du contrôle de bornes
O5 spec_hash modifié (spec mutée dans le test) l'item est ré-embeddé ET l'ancien vecteur reste lisible à côté (le spec_hash est dans le nom, l1-03.1) — les deux assertions
O6 ⭐ Un item en échec injecté (le double lève sur un id) compté failed, cause sur STDERR et dans embeddings/<model_id>.<spec_hash[:8]>.error.json ; les autres traités, exit 1 ; l'invariant boucle ; le manifest.json du Lot 0 est INCHANGÉ — hash du fichier comparé avant/après dans le test. ⚠ Revue E-1 : la v1 de cet oracle faisait réécrire le manifeste d'ingestion, détruisant la trace du Lot 0
O6b ⭐ Reprise après échec : run suivant sur l'item qui a produit un .error.json, le double ne levant plus l'item est ré-embeddé (embedded l'inclut), le .error.json a disparu. Témoin de la sémantique « une erreur se rejoue » — sans lui, un corpus incomplet passerait avec des compteurs qui bouclent
O7 Site sans aucun chip dans la fenêtre exit 0, found == 0, message explicite — ce n'est pas une erreur
O8 just check vert, hors ligne

Non testé par cette fiche : le comportement sur les 5 793 chips (l1-03.3) · les temps (l1-04.1) · la qualité des vecteurs · la concurrence.

Notes / pistes

⚠ Politique de test : pas de matrice d'options, pas de test par combinaison de drapeaux. Ce qui mérite un test ici, ce sont les invariants — conservation, idempotence, filtre — et chacun dans les deux sens.
