# [l1-04.2] — Le levier le moins cher : où sont lus les fichiers

> Fiche de backlog : sert de **brief (prompt)** pour l'IA.

## Objectif

Chiffrer ce que coûte la lecture du corpus **à travers le montage Windows** de WSL2, et ce
qu'on gagnerait à copier l'échantillon dans le système de fichiers natif. C'est le levier le
moins cher du lot : s'il est significatif, il s'applique sans toucher au modèle.

## Contexte et périmètre

`scripts/bench_io.py` — un script, pas un module de production.

Le corpus vit sur `D:\datas\tiny-wae`, atteint depuis WSL2 en `/mnt/d/...` via **drvfs**.
Le Lot 0 a déjà mesuré ce que cette couche coûte : `just install` y recopiait **696 Mo**
faute de liens durs. Une passe complète sur les embeddings, c'est **~16 Gio à lire à travers
elle**.

Protocole, à respecter strictement pour que la comparaison veuille dire quelque chose :

1. prendre **le même échantillon** de N chips (N ≈ 50) ;
2. mesurer la phase `load` de `l1-04.1` **depuis `/mnt/d`** ;
3. **copier** l'échantillon dans un répertoire du système de fichiers natif (`~/`), mesurer
   à nouveau ;
4. ⚠ **vider le cache disque entre les deux mesures**, ou faire les deux mesures **plusieurs
   fois en alternance** — sinon on mesure le cache du système, pas le montage. Dire dans le
   Résumé laquelle des deux méthodes a été retenue.

**Hors périmètre** : toute modification du pipeline · l'automatisation d'une copie locale
(si le levier est significatif, la décision d'en faire une étape appartient à `l1-06.H`) ·
le NAS, qui n'est pas utilisé ici.

## Définition de « terminé »

- [ ] `scripts/bench_io.py` livré, lançable par `just script bench_io`.
- [ ] Les deux mesures effectuées sur le **même** échantillon, protocole documenté.
- [ ] Écart publié **en pourcentage et en valeur absolue**, sur la phase `load` **et** sur le total.
- [ ] Extrapolation à 5 793 chips écrite noir sur blanc.

## Oracle / recette (figé AVANT implémentation)

| # | Critère mesuré | Seuil de succès |
|---|---|---|
| O1 | Les deux mesures portent sur le **même ensemble d'`item_id`** | ensembles **identiques** — vérifié dans le script, pas supposé |
| O2 | Le protocole anti-cache est appliqué | déclaré explicitement dans le JSON de sortie (`cache_policy: "alternating"` ou `"dropped"`) ; **un run sans politique déclarée est invalide** |
| O3 | Écart drvfs ↔ natif sur la phase `load` | **publié**, avec la méthode. Aucun seuil : c'est une mesure |
| O4 | Extrapolation | temps de lecture des 5 793 chips dans les deux cas, avec le **dénominateur** (N chips mesurés) et la mention explicite que c'est une extrapolation linéaire, donc optimiste |

**Non testé par cette fiche** : le comportement sur un autre montage (NAS, SSD externe) ·
l'effet du cache page de Windows, hors de portée · le gain réel après copie, qui dépendrait
du temps de copie lui-même — à mentionner s'il est du même ordre que le gain.

## Notes / pistes

⚠ **Le piège de cette fiche est le cache disque.** Mesurer `/mnt/d` puis la copie locale
juste après revient souvent à mesurer deux fois le cache — et à conclure « aucune
différence ». L'alternance répétée est la parade la plus simple sur WSL2, où vider le cache
proprement demande des droits.

⚠ Si le gain est **négligeable**, c'est un excellent résultat : il élimine une hypothèse et
le rapport peut le dire en une ligne. Un levier mesuré nul est un levier utile.

⚠ **Politique de test** : aucun test unitaire. C'est un script de mesure ; sa correction se
juge sur le protocole, pas sur des assertions.
