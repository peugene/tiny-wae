Fiche de backlog : sert de brief (prompt) pour l'IA. Révisée post-revue v1 (E-33 : O2 mécanisé ; dimensions corrigées 384).

Objectif

Prouver que le port de l1-01.3 tient sa promesse : la même fonction produit un vecteur avec Clay et avec TerraMind, sans branche conditionnelle chez l'appelant.

C'est un critère de sortie du Lot 1, et c'est aussi ce qui rend le banc comparatif honnête : si l'appelant devait connaître le modèle, on ne comparerait plus deux modèles mais deux chemins de code.

Contexte et périmètre

tests/test_model_substitution.py — plus, si nécessaire, un petit correctif dans les adapters pour lever une divergence constatée.

⚠ Leçon out-01 du Lot 0 : la substituabilité à un Protocol n'est pas vérifiée par un test d'exécution. Un double qui « marche » peut violer le contrat statique. C'est mypy --strict qui est l'oracle principal ici — le test d'exécution ne fait que confirmer que les deux vecteurs sortent.

Ce qu'il faut écrire :

  • une seule fonction de consommation, annotée EmbeddingModel, sans isinstance, sans cast, sans type: ignore ;
  • elle est appelée avec les trois implémentations : FakeEmbeddingModel, Clay, TerraMind ;
  • ⭐ vérification que les dimensions diffèrent — 1024 (Clay) contre 384 (TerraMind), cf. la table du chapeau l1-02 — et que le code d'appel ne s'en soucie pas : c'est le cœur de la démonstration, un appelant qui supposerait une dimension fixe serait rouge ici. (Le « 768 » qui figurait ici jusqu'à la revue v3 venait de la carte HF de TerraMind, qui est fausse — le code source dit 384. Corrigé en O2 dès la v1, le corps de la fiche avait survécu : c'est exactement le motif « l'implémenteur lit le corps avant l'oracle ».)

Hors périmètre : toute comparaison de qualité entre les deux (l1-05) · toute mesure de temps (l1-04).

Définition de « terminé »

  • [ ] Une fonction de consommation unique, annotée, sans branche par modèle.
  • [ ] Les trois implémentations passent par elle.
  • [ ] mypy --strict vert sans aucun cast ni type: ignore dans le chemin.
  • [ ] Le registre resolve_model connaît les trois model_id.

Oracle / recette (figé AVANT implémentation)

# Critère mesuré Seuil de succès
O1 ⭐ mypy --strict sur le module de consommation vert, zéro cast, zéro type: ignore — grep sur le fichier pour le prouver mécaniquement. ⚠ Portée de l'interdiction, précisée en revue v3 (A-13) : elle vise le consommateur, pas les adapters. pyproject.toml pose ignore_missing_imports = true, donc torch, claymodel et terratorch rendent Any : --strict ne mord pas à l'intérieur des adapters, et convertir la sortie du modèle par np.asarray(...) à la frontière y est la bonne pratique, pas une entorse
O2 La même fonction, appelée avec les 3 implémentations, sur la même fixture 3 vecteurs float32 sans NaN ; dimensions 1024 · 384 · celle du double — et aucune branche par modèle : grep mécanique sur la fonction, aucune occurrence de model_id ==, isinstance(, ni clay|terramind (insensible à la casse)
O3 resolve_model sur les 3 identifiants rend la bonne implémentation ; un id inconnu lève en listant les 3
O4 just check vert, hors ligne

Non testé par cette fiche : la comparabilité sémantique des deux vecteurs — un CLS et une moyenne de patchs ne vivent pas dans le même espace, on ne les compare jamais entre eux, seulement chacun à lui-même au fil du temps. C'est écrit ici parce que c'est le contresens le plus facile à commettre au Lot 2.

Notes / pistes

Cette fiche est courte et elle est un critère de sortie du lot : c'est normal. Sa valeur n'est pas dans le volume de code mais dans le fait qu'elle rende rouge un port qui fuirait — par exemple si un adapter exposait une méthode que l'autre n'a pas et qu'un appelant s'était mis à l'utiliser.

⚠ Politique de test : pas de test paramétré sur des matrices de combinaisons de modèles et d'options — la démonstration tient dans un chemin unique parcouru par trois implémentations.
