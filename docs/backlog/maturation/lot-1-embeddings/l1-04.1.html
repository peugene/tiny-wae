Fiche de backlog : sert de brief (prompt) pour l'IA.

Objectif

Mesurer où passe le temps d'un embedding, phase par phase, et la mémoire crête. C'est la fondation des quatre fiches suivantes : sans elle, tous les leviers seraient mesurés à travers un total qui mélange l'I/O et le calcul.

Contexte et périmètre

src/tiny_wae/cli/bench.py + src/tiny_wae/adapters/bench_probe.py.

⭐ La séparation des trois phases est le cœur de la fiche :

Phase Ce qu'elle couvre
load lecture des deux rasters, rééchantillonnage 2×2, normalisation → tenseur prêt
forward passage dans le modèle → vecteur
write écriture du .npy et du compagnon

L'instrumentation enveloppe le code existant (l1-01.2, adapters, l1-03.1) — elle ne le modifie pas. Un décorateur, un gestionnaire de contexte, peu importe : le code de production ne doit pas se remplir de chronomètres.

À mesurer par chip, et à agréger : temps par phase (médiane et p90, pas seulement la moyenne — une moyenne masque les à-coups du système de fichiers), RAM crête du processus, octets lus.

Interface :

just run bench --model clay-v1.5 --site A01 --n 50 [--out bench.json]
  • --n : nombre de chips, pour que le banc reste court ;
  • ⭐ une phase de chauffe (2-3 chips exclus des statistiques) : le premier passage d'un modèle PyTorch inclut des allocations et des optimisations qui ne se reproduisent pas. Les inclure fausserait la médiane vers le haut.

Sortie : JSON, jamais des logs à relire à l'œil.

Hors périmètre : tout levier (l1-04.2 à .4) · le rapport comparatif (l1-04.5) · toute qualité.

Définition de « terminé »

  • [ ] cli/bench.py livré, découvert automatiquement, sortie JSON.
  • [ ] Trois phases chronométrées séparément, médiane et p90.
  • [ ] RAM crête du processus mesurée.
  • [ ] Chauffe exclue des statistiques, nombre de chips de chauffe écrit dans le JSON.
  • [ ] Le code de production n'a pas été modifié pour l'instrumentation.
  • [ ] tests/test_bench.py — court.

Oracle / recette (figé AVANT implémentation)

# Critère mesuré Seuil de succès
O1 ⭐ L'instrumentation compte ce qu'elle prétend compter : un double qui dort 100 ms dans la phase forward le JSON attribue ~100 ms à forward et quasi rien aux deux autres. C'est le seul test qui prouve que la séparation n'est pas décorative
O2 Somme des trois phases contre temps total mesuré de bout en bout écart < 5 % — sinon du temps se perd hors instrumentation et les leviers seront mesurés à travers un trou
O3 Run avec --n 10 sur le double JSON complet : 3 phases × (médiane, p90), RAM crête, nombre de chips, chauffe, model_id, spec_hash
O4 Deux runs identiques sur le double les champs de contexte sont identiques ; les temps varient — aucun seuil sur les temps, c'est une mesure, pas une assertion
O5 just check vert. ⚠ bench n'entre PAS dans le gate — c'est un outil de mesure, il se lance à la main

Non testé par cette fiche : toute valeur de temps réelle (elles sont publiées, pas assertées) · les leviers · la représentativité de --n 50 sur 5 793 chips — c'est justement ce que l'extrapolation de l1-04.5 devra assumer et déclarer.

Notes / pistes

⚠ Pourquoi la médiane ET le p90. Sur un montage drvfs, quelques lectures très lentes suffisent à décaler une moyenne. La médiane dit le cas courant, le p90 dit ce qu'on subit régulièrement. Publier les deux évite une extrapolation trop optimiste ou trop pessimiste.

⚠ Politique de test : O1 et O2 sont les deux tests qui portent quelque chose — ils prouvent que l'instrumentation ne ment pas. Le reste relève de la forme du JSON.

Pistes : time.perf_counter suffit ; pour la RAM crête, resource.getrusage (Linux/WSL2) ou tracemalloc — au choix, à condition de dire lequel dans le JSON, parce qu'ils ne mesurent pas la même chose.
