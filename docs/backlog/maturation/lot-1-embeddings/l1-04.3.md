# [l1-04.3] — Les leviers de calcul

> Fiche de backlog : sert de **brief (prompt)** pour l'IA.

## Objectif

Chiffrer quatre réglages qui changent le débit sans changer le modèle, et **chiffrer le coût
de la variante 10 m** que le lot a choisi de ne pas produire — pour que la décision reste
informée si le Lot 2 la rouvre.

## Contexte et périmètre

`scripts/bench_levers.py`.

Les quatre leviers, par ordre d'intérêt attendu :

1. ⭐ **Résolution d'entrée.** Le lot produit `whole_chip` en 20 m — un tenseur 256×256, soit
   une tuile Clay. La variante 10 m (512×512) en ferait **quatre**. **Mesurer le facteur
   réel sur un échantillon** (quelques dizaines de chips), sans produire la variante en
   masse. Attendu ≈ ×4 côté forward, mais c'est à vérifier : le chargement, lui, ne change
   pas beaucoup. **C'est ce chiffre qui rend réversible la décision du chapeau `l1-01`.**
2. **Taille de batch.** Embedder les chips un par un ou par paquets de 2, 4, 8. Sur CPU le
   gain est souvent réel mais plafonne vite, et la RAM crête monte — **mesurer les deux
   ensemble**, un gain de débit payé par un dépassement mémoire n'en est pas un.
3. **Threads BLAS** (`torch.set_num_threads`). Balayer 1, 2, 4, et le nombre de cœurs
   physiques. ⚠ **Noter le nombre de cœurs de la machine dans le JSON** — sans lui, la
   mesure n'est pas interprétable.
4. **Workers du backfill** (`l1-03.3`). ⚠ **Le piège** : ici le goulot est le calcul, pas le
   réseau. N workers × M threads BLAS = contention, et **sur-paralléliser peut ralentir**.
   Mesurer le produit, pas les deux séparément : `(workers=1, threads=8)` contre
   `(workers=4, threads=2)` à charge égale.

Chaque levier est mesuré **pour les deux modèles** — leurs profils diffèrent (1024 tokens
contre 196), rien ne dit que le réglage optimal soit le même.

**Hors périmètre** : la quantification (`l1-04.4`) · l'I/O (`l1-04.2`) · toute réécriture du
code des adapters — on règle des paramètres, on n'optimise pas le code.

## Définition de « terminé »

- [ ] `scripts/bench_levers.py` livré, sortie **JSON**, lançable par `just script bench_levers`.
- [ ] Les 4 leviers mesurés, **pour les 2 modèles**.
- [ ] Contexte machine dans le JSON : cœurs physiques et logiques, RAM, version de torch.
- [ ] Le facteur 10 m / 20 m est **publié en toutes lettres**.
- [ ] RAM crête relevée pour chaque taille de batch.

## Oracle / recette (figé AVANT implémentation)

| # | Critère mesuré | Seuil de succès |
|---|---|---|
| O1 | ⭐ **Facteur de résolution** : forward en 512×512 contre 256×256, même modèle, même échantillon | facteur **publié**, avec le nombre de chips mesurés. Aucun seuil — c'est le chiffre qui manquait à la décision du chapeau `l1-01` |
| O2 | Balayage de batch (1, 2, 4, 8) | débit **et** RAM crête pour chaque valeur ; le point où la RAM dépasse la moitié de la RAM machine est **signalé** |
| O3 | Balayage de threads BLAS | débit par valeur, **avec le nombre de cœurs de la machine dans le même JSON** |
| O4 | ⭐ **Contention** : `(workers=1, threads=N)` contre `(workers=N, threads=1)` à charge égale | les deux **publiés**. Si le second est plus lent, le dire explicitement — c'est un résultat, pas un échec |
| O5 | Chaque mesure porte le **même échantillon d'`item_id`** entre configurations | ensembles identiques, vérifié dans le script |
| O6 | Reproductibilité | chaque configuration mesurée **au moins 2 fois** ; si l'écart entre les deux passes dépasse **20 %**, la mesure est déclarée instable et le nombre de répétitions augmenté |

**Non testé par cette fiche** : le comportement sous charge concurrente d'autres
applications (la machine est un poste de travail — à mentionner comme limite) · les gains
possibles d'une réécriture du code · le GPU.

## Notes / pistes

⚠ **Le levier 4 est celui qui surprendra le plus.** Le backfill du Lot 0 utilisait 6 workers
et c'était le bon réglage — parce qu'il attendait le réseau. Transposer ce 6 ici serait une
erreur, et c'est une erreur qu'on ne voit pas : le run se termine, plus lentement, sans rien
signaler.

⚠ **Politique de test** : aucun test unitaire sur ce script. Ce sont des mesures ; leur
qualité tient au protocole (même échantillon, répétitions, contexte machine consigné), pas à
des assertions pytest.
