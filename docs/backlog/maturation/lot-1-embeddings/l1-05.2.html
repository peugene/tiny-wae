Objectif

Établir dans quelles conditions un embedding est reproductible. C'est ce dont dépend l'idempotence de l1-03.2 — et, plus loin, la validité de toute comparaison de vecteurs au Lot 2.

Contexte et périmètre

scripts/bench_determinism.py.

⭐ La formulation a été corrigée pendant le cadrage, et la nuance compte :

  • À configuration fixée — même modèle, même nombre de threads BLAS, même entrée — l'identité est exigée. C'est ce que l'idempotence suppose : un vecteur resservi doit être celui qu'on aurait recalculé.
  • Entre configurations de threads, l'écart est mesuré, pas exigé nul. l1-04.3b fait précisément varier ce paramètre pour mesurer le passage à l'échelle : exiger le bit à bit partout contredirait ce levier.

Et ce second chiffre est utile en soi : s'il n'est pas nul, cela signifie qu'au Lot 2 on ne pourra pas comparer sans précaution des vecteurs calculés à des moments différents, sur des machines réglées différemment. Mieux vaut le savoir maintenant.

Ce que le script mesure, sur l'échantillon de banc gelé par l1-04.1 (même liste d'item_id que les fiches de levier) et pour les deux modèles :

  1. deux passages, threads figés → égalité bit à bit attendue ;
  2. passages à 1, 2, 4, 8 threads → ⭐ similarité cosinus au vecteur de référence (une similarité : 1 = identiques), médiane et minimum — le minimum d'une similarité est bien le pire cas, ce qui est l'information cherchée. (Le corps disait « distance » alors que O3 dit « similarité » : lu à l'envers, le « minimum » devenait le meilleur cas — l'erreur exacte que la revue v1 avait déjà corrigée dans l'oracle.) ;
  3. deux processus distincts, mêmes réglages → même question. ⚠ C'est un cas différent du premier : l'ordre d'allocation mémoire et l'initialisation des bibliothèques natives peuvent changer d'un processus à l'autre.

Hors périmètre : la quantification (l1-04.4, qui a sa propre mesure de fidélité) · les performances · toute vérité terrain.

Définition de « terminé »

  • [ ] scripts/bench_determinism.py livré, sortie JSON, lançable par just script.
  • [ ] Les 3 cas mesurés, pour les 2 modèles.
  • [ ] La graine et le nombre de threads sont écrits dans le JSON — sans eux la mesure n'est pas reproductible.
  • [ ] ⭐ Si O1 échoue : la fiche se termine en ROUGE DÉCLARÉ, elle ne se bloque pas. Le JSON porte determinism_violated: true avec l'écart mesuré, un constat d'anomalie est écrit au Résumé, et la fiche passe en fait/ — le point 6 de l1-06.H devient alors bloquant pour la recette du lot. (Motif : la formulation « pas terminable » créait un interblocage — l1-06.H a l1-05.2 dans ses depends_on, donc une fiche qui ne descend jamais en fait/ rendrait l'arbitrage humain, et avec lui la clôture du lot, inatteignables. Le rouge doit remonter, pas immobiliser.) ⚠ Ce qui reste interdit, et c'est le fond de la règle : aucune tolérance ne se fixe après coup en la calant sur la valeur observée. Le chiffre se publie, Philippe tranche.

Oracle / recette (figé AVANT implémentation)

# Critère mesuré Seuil de succès
O1 ⭐ Deux passages, même processus, threads figés, sur l'échantillon gelé de l1-04.1 assertion DURE : 100 % de array_equal. Si elle échoue → rouge déclaré (determinism_violated: true + écart mesuré), fiche terminée quand même, point 6 de l1-06.H bloquant pour la recette — car la sémantique d'idempotence de l1-03.2 devra être révisée. ⚠ Revue E-22 : la v1 disait « si non : écart publié », ce qui rendait l'oracle jamais rouge ; revue v3 : « pas terminable » le rendait bloquant pour le lot entier
O2 Deux processus distincts, mêmes réglages même critère, résultat publié séparément de O1 — c'est un cas différent
O3 Balayage de threads (1, 2, 4, 8) similarité cosinus au vecteur de référence : médiane ET minimum publiés — le minimum d'une similarité EST le pire cas (revue K-17 : la v1 publiait le minimum d'une distance, c'est-à-dire le MEILLEUR cas). ⭐ Qualification à trois états, SANS seuil de passage (décision Philippe du 25/08) : identical (bit à bit) · negligible (min ≥ 0,9999) · significant (en deçà) — chaque état est un résultat publié, aucun ne fait échouer la fiche. C'est l1-06.H (point 6) qui décide de la tolérance à retenir. ⚠ Ne pas réutiliser ici le 0,999 de l1-04.4 : c'est le plancher acté pour la quantification, un tout autre phénomène — l'importer en douce reviendrait à créer un seuil décisionnel que personne n'a arbitré (revue v3, E-16 amendé par le réfuteur)
O4 Un chip modifié d'un bloc 2×2 mis à 0 sur une bande vecteur différent (not array_equal) — c'est l'assertion dure du témoin négatif. La similarité observée est publiée avec, à côté, la plus petite similarité mesurable sur cette machine (min_detectable, relevée en O1/O3) : si la perturbation tombe dans le bruit, on le lit au lieu de buter sur un seuil sans issue. ⚠ Revue v3, E-30 : « similarité < 0,999999 » ne laissait aucune conduite à tenir pour une valeur mesurée à 0,9999995. ⚠ Revue E-34 : un seul pixel 10 m pèse ¼ de pixel après l'agrégation 2×2 et pouvait passer sous le bruit float32 — d'où le bloc, pas le pixel
O5 JSON de sortie graine, threads, versions torch/paquet, model_id, nombre de chips, et torch.get_float32_matmul_precision() — l'import de claymodel la change globalement (revue F-14) ; le banc lance un processus par modèle

Non testé par cette fiche : la reproductibilité sur une autre machine — hors de portée et explicitement hors périmètre du POC · l'effet de la version de torch dans le temps · la quantification.

Notes / pistes

⚠ O4 est le garde-fou le plus important de la fiche. Trois critères d'égalité et aucun témoin négatif, c'est exactement la configuration où un bug qui renvoie toujours le même vecteur passe au vert.

⚠ ⭐ « Pas de test » ne veut PAS dire « hors du filet » (revue v4, m2) : pyproject.toml:146 pose files = ["src", "tests", "scripts"] — mypy --strict couvre scripts/, ce script compris. (Et assert y est permis : l1-00 pré-pose l'exemption S101 pour scripts/bench_*.py — c'est ce qui rend exécutable l'« assertion DURE » d'O1.)

⚠ Politique de test : script de mesure, aucun test unitaire. La vérification, c'est la mesure elle-même.

Pistes : torch.use_deterministic_algorithms(True) et torch.set_num_threads(N) sont les deux leviers habituels ; le premier peut lever sur certains opérateurs — si c'est le cas, le dire plutôt que de le contourner silencieusement.
