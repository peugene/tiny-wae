# [l1-03.3] — Le backfill des embeddings

> Fiche de backlog : sert de **brief (prompt)** pour l'IA.
> **Révisée post-revue v1** (E-14, E-15, E-30, S-18) : O1 et O4 réécrits — l'un était
> impossible par idempotence, l'autre satisfaisable à vide ; clé de settings dédiée.
> **Révisée post-revue v3** (V-21, V-10) : le **type de pool** est désormais écrit — il
> détermine si le levier « threads » de `l1-04.3b` mesure quelque chose ; la clé de settings
> est pré-posée par `l1-00`.

## Objectif

Passer les 25 sites en une commande, avec un pool de workers, une reprise naturelle et une
interruption qui ne laisse rien de cassé. C'est l'outil qui produira réellement le corpus de
vecteurs pour `l1-05`.

## Contexte et périmètre

`src/tiny_wae/cli/embed_backfill.py`.

⚠ **Lire `cli/backfill.py` du Lot 0 avant d'écrire** — le patron existe : pool, isolation
par site, distinction entre échec métier et amont injoignable, compteurs agrégés. Ici c'est
plus simple : pas de réseau, donc pas de cas « injoignable ».

Interface :

```
just run embed-backfill --model clay-v1.5 [--sites A01,B09] [--workers N] [--cloud-max N] [--from …] [--to …]
```

Points d'attention :

- ⭐ **Le parallélisme sur CPU n'est pas gratuit ici.** Contrairement au backfill du Lot 0,
  qui attendait le réseau, celui-ci est **limité par le calcul** : N workers se disputent
  les mêmes cœurs, et chaque worker peut lui-même lancer plusieurs threads BLAS.
  **Sur-paralléliser peut ralentir.** Le défaut doit être **prudent** (workers = 1 ou 2), et
  la mesure du bon réglage appartient à `l1-04.3b` — cette fiche fournit le levier, pas sa
  valeur.
- ⭐ **Type de pool : `ThreadPoolExecutor`, tranché ici** (revue v3, V-21). Le patron du
  Lot 0 (`adapters/backfill.py`) en est un, et cette fiche le reprend — la fiche ne le
  disait nulle part, ce qui laissait planer une ambiguïté lourde de conséquences :
  avec des **threads**, `torch.set_num_threads` est process-global et s'applique bien aux
  workers ; avec des **processus**, il ne s'hériterait pas et le levier « threads » de
  `l1-04.3b` mesurerait autre chose que ce qu'il croit. Le dire une fois évite d'avoir à
  le déduire. *(Si un pool de processus devenait nécessaire pour contourner le GIL, ce
  serait une décision de `l1-04.3b`, prise sur mesure, et elle imposerait de propager
  `OMP_NUM_THREADS`/`MKL_NUM_THREADS` par l'environnement.)*
- **L'isolation par site** reste la bonne granularité : un site en échec n'empêche pas les
  autres.
- **La reprise est naturelle** : l'idempotence de `l1-03.2` fait qu'un relancement saute ce
  qui existe. Aucun fichier d'état à maintenir.
- ⭐ **Clé de settings DÉDIÉE : `embed_workers`** (défaut 1) — surtout pas
  `backfill_workers`, qui existe déjà (Lot 0, défaut 6, calibré pour un goulot RÉSEAU) :
  réutiliser la clé dégraderait l'ingestion par effet de bord silencieux (revue S-18).
  ⚠ La clé est **pré-posée par `l1-00`** dans `settings.yaml` et dans
  `config_io._INT_FIELDS` : cette fiche la **consomme**, elle n'écrit pas dans ces fichiers
  (revue v3, V-10 — c'est ce qui supprime l'écriture concurrente sur la configuration).
- **Interruption (SIGINT)** : sortie non nulle, et **tous les vecteurs écrits restent
  relisibles** — c'est l'écriture atomique de `l1-03.1` qui le garantit.

**Hors périmètre** : la campagne réelle elle-même (`l1-05.3.H`, geste humain) · les
mesures de débit (`l1-04`) · le choix du nombre de workers (`l1-04.3b`).

## Notes / pistes

⚠ **Ne pas transposer aveuglément le backfill du Lot 0.** Là-bas, 6 workers étaient bons
parce que le goulot était le réseau. Ici le goulot est le CPU, et un modèle PyTorch utilise
déjà plusieurs threads : **6 workers × N threads = contention**. C'est un piège classique et
il se mesure, il ne se devine pas.

⚠ **Politique de test** : tout se teste sur le double. Le test d'interruption (O4) est celui
qui a le plus de valeur — ne pas le sacrifier au profit de tests de compteurs, qui sont plus
faciles à écrire et attrapent beaucoup moins.
