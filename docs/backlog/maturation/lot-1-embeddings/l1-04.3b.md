# [l1-04.3b] — Threads et contention

> **Issue de la scission de `l1-04.3`** ; O de stabilité réécrit (revue E-11 : le « 20 % »

> **Révisée post-revue v3** (V-24, V-21, V-09) : effort relevé à **M** — elle porte une
> dépendance de plus que sa sœur, un protocole via un vrai CLI, et c'est elle qui doit
> prouver que le levier « threads » atteint réellement les workers.

⛔ **Fiche de mesure CPU — ne se dispatche JAMAIS en parallèle** d'une autre fiche de banc
(`l1-04.2`, `l1-04.3a`, `l1-04.4`, `l1-05.2`) ni d'aucune charge CPU concurrente. C'est la
plus sensible des cinq : elle mesure précisément la **contention**.

## Objectif

Trouver le bon réglage de parallélisme pour la campagne : combien de threads BLAS, combien
de workers — et surtout mesurer la **contention** entre les deux, qui peut rendre le
parallélisme contre-productif sur un goulot CPU.

## Contexte et périmètre

`scripts/bench_levers_b.py`, sortie JSON, pour **les deux modèles**.

1. **Threads BLAS** (`torch.set_num_threads`) : 1, 2, 4, nombre de cœurs physiques.
   ⚠ Le nombre de cœurs de la machine est **écrit dans le JSON** — sans lui la mesure n'est
   pas interprétable.
2. ⭐ **Contention** : à charge égale, `(workers=1, threads=N)` contre
   `(workers=N, threads=1)` via `embed-backfill` (`l1-03.3`). Si le second est plus lent,
   le dire — c'est un résultat, pas un échec. Le réglage retenu est celui que la campagne
   (`l1-05.3.H`) utilisera.

Échantillon : **celui que `l1-04.1` a gelé**, même liste d'`item_id` que les autres fiches
de levier.

⭐ **Le levier atteint-il vraiment les workers ?** (revue v3, V-21). `l1-03.3` utilise un
`ThreadPoolExecutor` — même processus, donc `torch.set_num_threads` **s'applique** aux
workers. C'est l'hypothèse de travail, et elle est fondée ; mais elle ne se suppose pas :
O1 exige de **relever depuis un worker** `torch.get_num_threads()` et `OMP_NUM_THREADS`, et
de les écrire dans le JSON. Si un jour le pool devenait un pool de **processus**, le réglage
cesserait d'être hérité et cette mesure — pas une relecture de code — le dirait tout de
suite. *(Un balayage de threads qui ne bouge pas le débit alors que les valeurs relevées ne
bougent pas non plus est un artefact ; le même balayage avec des valeurs relevées correctes
est un vrai résultat. La différence ne se voit que si on relève.)*

**Hors périmètre** : résolution et batch (`l1-04.3a`) · la quantification.

## Définition de « terminé »

- [ ] JSON par modèle : débit par nombre de threads, les deux configs de contention,
      contexte machine (cœurs physiques/logiques, RAM, version torch).
- [ ] Le réglage recommandé pour la campagne est écrit en toutes lettres.

## Oracle / recette (figé AVANT implémentation)

| # | Critère mesuré | Seuil de succès |
|---|---|---|
| O1 | Balayage threads — **et relevé des threads effectifs DEPUIS un worker** | débit par valeur, cœurs machine, **`torch.get_num_threads()` et `OMP_NUM_THREADS` tels que vus dans le worker**, tous dans le même JSON. Le relevé doit **suivre** la consigne (threads=2 demandés → 2 relevés) ; s'il ne la suit pas, le balayage ne mesure rien et **c'est ce constat-là** qui est le résultat |
