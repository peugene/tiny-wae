# [l1-03.1] — Où vivent les vecteurs, et comment on sait qu'ils sont à jour

> Fiche de backlog : sert de **brief (prompt)** pour l'IA.

## Objectif

Définir le format d'écriture d'un vecteur et de son compagnon, et la **clé d'idempotence**
qui permettra à `l1-03.2` de ne rien recalculer inutilement.

## Contexte et périmètre

`src/tiny_wae/adapters/vectors.py`.

**Emplacement retenu** : à côté du chip, comme les manifestes du Lot 0 —
`<data_root>/<site>/<item_id>/embeddings/<model_id>.npy` et `<model_id>.json`. Motif : le
Lot 0 a démontré que ranger les artefacts **par item** rend l'intégrité vérifiable
répertoire par répertoire, sans index global à maintenir.

⚠ **Le corpus vit sur `D:\datas\tiny-wae`, hors dépôt.** Les vecteurs y seront écrits aussi :
prévoir que `data_root` soit configurable (il l'est déjà, Lot 0) et **ne jamais écrire dans
`./data` par défaut** depuis un test.

À livrer :

- `write_vector(dir, model_id, vector, meta)` — écriture **atomique** (fichier temporaire
  puis `Path.replace`), comme `write_manifest` du Lot 0. Un run interrompu ne doit pas
  laisser un `.npy` tronqué qui serait relu comme valide.
- `read_vector(dir, model_id) -> Vector | None` — `None` si absent, erreur typée si corrompu.
- ⭐ `embedding_key(grid_hash, model_id, spec_hash) -> str` — la clé d'idempotence.
  **Les trois composantes, pas deux.** Elle est écrite dans le compagnon ; `l1-03.2`
  comparera la clé stockée à la clé courante pour décider de recalculer ou de sauter.
- Le **compagnon JSON** : `item_id`, `site_id`, `datetime`, `cloud_pct`, résumé SCL,
  `model_id`, `dim`, `spec_hash`, `grid_hash`, `embedding_key`, version du paquet,
  horodatage. C'est le contexte dont le Lot 2 aura besoin.

**Hors périmètre** : le CLI (`l1-03.2`) · toute base de données · tout index global.

## Définition de « terminé »

- [ ] `adapters/vectors.py` livré, `mypy --strict` vert.
- [ ] Écriture atomique, relecture, erreur typée sur fichier corrompu.
- [ ] `embedding_key` combine les trois composantes.
- [ ] `tests/test_vectors.py` — court.

## Oracle / recette (figé AVANT implémentation)

| # | Critère mesuré | Seuil de succès |
|---|---|---|
| O1 | Aller-retour écriture/lecture d'un vecteur littéral + son compagnon | identité **champ à champ** du compagnon ; vecteur identique au bit près, dtype et forme préservés |
| O2 | ⭐ `embedding_key` : **trois mutations séparées** — `grid_hash` modifié · `model_id` modifié · `spec_hash` modifié | clé **différente** dans les trois cas ; et clé **identique** quand les trois sont inchangés. Les deux sens, sinon la clé ne prouve rien |
| O3 | Fichier temporaire orphelin déposé dans le répertoire (interruption simulée) | `read_vector` **ne le voit pas** ; pas de vecteur fantôme |
| O4 | `.npy` tronqué à la main | erreur **typée**, pas un tableau silencieusement faux |
| O5 | `just check` | vert |

**Non testé par cette fiche** : la concurrence réelle entre workers (`l1-03.3`) · les
volumes (`l1-04`) · toute valeur d'embedding.

## Notes / pistes

⚠ **Pourquoi les trois composantes de la clé.** Avec seulement `grid_hash` + `model_id`, un
changement de résolution d'entrée (spec 20 m → 10 m) resservirait des vecteurs périmés
**sans que rien ne le signale**. C'est exactement le mécanisme du `grid_hash` du Lot 0,
étendu à la spec — et c'est ce qui rend réversible la décision « un vecteur par chip » du
chapeau `l1-01`.

Format : `.npy` plutôt que Parquet — un vecteur par fichier, pas de dépendance
supplémentaire, et `numpy` est déjà au contrat. Si le Lot 2 a besoin d'un format colonne,
il fera la conversion, ce n'est pas le travail de ce lot.
