[l0-05.2] — CLI update

Objectif

Le run quotidien : pour chaque site, fenêtre depuis l0-05.1, ingest, résumé honnête.

Périmètre (fichiers nommés)

  • src/tiny_wae/cli/update.py (auto-découvert) : update [--sites all] [--now …] — une ligne par site sur STDERR, résumé final (« 25 sites, N avec du nouveau, M à jour, K échecs »). Codes de sortie (règle du chapeau l0-01, obligatoire dans les 3 CLIs qui appellent l'amont) : OK=0 aucun échec · FAILURE=1 au moins un échec avec au moins un succès, et site vierge (message nommant backfill) · ⭐ INCONCLUSIVE=3 si TOUS les échecs sont d'origine réseau et qu'aucun site n'a abouti — c'est le CLI destiné au cron, celui que personne ne regarde tourner : une panne d'earth-search doit s'y distinguer d'un bug du pipeline.
  • Rattrapage mensuel des retraitements tardifs : DOCUMENTÉ (README + une ligne dans la sortie du CLI le rappelant chaque 1er du mois via la date injectée) — non automatisé.
  • Tests sur FixtureSource + corpus manifestes.

Définition de « terminé »

  • [ ] CLI + tests ; README complété (commande cron type + rattrapage).

Oracle / recette

# Critère Seuil
O1 Fixture : 2 items nouveaux disponibles après last_datetime ingested == 2 EXACTEMENT (témoin positif — un update inopérant échoue ici)
O2 update ×2 d'affilée (E-d) 1er run (sur la fixture d'O1) : assets_read > 0 ; 2e run : ingested == 0 ET assets_read == 0
O3 Trou simulé (manifestes du dernier mois retirés sur 1 site, fixtures couvrant le mois — livrées par l0-03.5) ensemble (item_id, statut) du site restauré à l'identique ; hashes des manifestes des autres sites inchangés
O4 Site vierge exit 1, message « backfill »
O5 Échec injecté sur 1 site exit 1, les autres traités (compteurs le prouvent)
O5bis Amont injoignable sur TOUS les sites exit 3 (INCONCLUSIVE), distinct de O5 et du site vierge (O4, exit 1)
O6 just check vert, hors ligne
